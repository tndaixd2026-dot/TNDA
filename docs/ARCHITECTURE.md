# 技術架構

## 設計目標

- **零成本**：只用 GitHub Pages、GitHub repo、GitHub Actions 與 Discord Webhook，公開 repo 全部免費。
- **公開 repo 也安全**：所有內容加密後才寫入；程式碼、檔名、提交訊息、Actions 紀錄都不含貼文內容。
- **不重複發文**：排程器、多台裝置同時運作時，同一則貼文在同一個頻道只會送出一次。
- **一份程式碼**：`src/core/` 同時給瀏覽器與排程器使用（Node 22.18+ 可以直接執行 TypeScript），兩邊的資料格式與發送規則不會分歧。

## 元件

```
瀏覽器（GitHub Pages）                GitHub repo                          GitHub Actions
┌──────────────────────┐   PUT     ┌──────────────────────────┐   讀取   ┌────────────────────┐
│ 智慧整理 parser.ts    │ ───────▶ │ 預設分支：程式碼、workflow │ ◀────── │ scheduler.yml       │
│ 訊息組裝 composer.ts  │  (加密)  │ tnda-data 分支：          │         │  每 5 分鐘           │
│ Discord 預覽          │          │   meta.json   金鑰檢查    │  寫回    │  node scripts/      │
│ 狀態 store.ts         │ ◀─────── │   channels.json（加密）   │ ◀────── │   scheduler.ts      │
│ 準時代發 ─────────────┼──┐       │   settings.json（加密）   │         └─────────┬──────────┘
└──────────────────────┘  │       │   posts/p_*.json（加密）  │                   │ Webhook
                          │       └──────────────────────────┘                   ▼
                          └─────────────────────────────────────────────▶  Discord 頻道
```

## 加密

- **同步金鑰**：160 位元亂數，以 Crockford Base32 顯示為 `TNDA-XXXX-…`（去掉易混淆字元，輸入時也容忍大小寫與 O/0、I/1）。
- **金鑰衍生**：HKDF-SHA256（salt `tnda-relay/v1`）→ AES-256-GCM 金鑰。
- **檔案格式**：`{"tnda":1,"alg":"A256GCM","iv":"…","ct":"…"}`；以檔案路徑作為 AAD，加密檔被搬到別的路徑就解不開。
- `meta.json` 存一段加密的檢查字串，用來確認輸入的金鑰正確。
- 排程器的金鑰存在 Actions Secret `TNDA_SYNC_KEY`。網站用 repo 的公開金鑰以 libsodium sealed box（tweetnacl + BLAKE2b 實作，已用 libsodium 交叉測試）加密後，透過 GitHub API 寫入。

## 資料模型（`src/core/types.ts`）

- `Post`：一則貼文。含 `sendAt`、`channels`、`payload`（Discord 訊息本體）、`draft`（可再編輯的結構化內容）、`deliveries`（每個頻道的結果）、`series`（提醒鏈）、`repeat`（每週重複）。
- `Delivery`：`pending → sending → sent | failed`，記錄嘗試次數、Discord 訊息 ID、錯誤、撤回／編輯時間。
- 貼文狀態由各頻道結果推算：全部成功 `sent`、部分失敗 `partial`、全部失敗 `failed`、還有要重試的 `scheduled`。

## 發送流程（`src/core/engine.ts`）

1. **認領**：讀取貼文最新版本 → 把待發送的頻道標成 `sending`（記錄由誰認領）→ 帶 sha 寫回。若 sha 不符（別人剛改過），重新讀取再試；若已經被別人認領或時間被改到未來，就放棄。
2. **發送**：只發送自己認領的頻道。`?wait=true` 取得訊息 ID，之後才能撤回或編輯。遇到 429 依 `retry_after` 等待重試；5xx 標記為可重試；404／401 等標記為不可重試並提示原因。
3. **寫回**：再讀一次最新版本，把自己處理過的頻道結果合併進去，帶 sha 寫回。
4. **重複貼文**：發送成功後建立下一次的貼文，訊息中的 `<t:unix>` 時間戳一起往後推。
5. **卡住的認領**：「發送中」超過 15 分鐘沒有結果（發送端中途中斷），標記為「狀態不明」並交給老師確認，不自動重發，避免重複。
6. **瀏覽器連不到 Discord**：訊息根本沒送出時，把頻道交還為 `pending`，並觸發排程器立即執行。

排程器在定時執行時會往前看 5.5 分鐘（比 5 分鐘的觸發間隔多一點，涵蓋觸發延遲），等到貼文的發送時間才送出，讓時間盡量準確；兩次執行的範圍重疊時，靠「認領」保證只送一次。

排程器每次執行會先用 `actions/checkout` 取出 `tnda-data` 分支，依 git blob sha 建立本機快取，再透過 API 讀檔案清單。這樣讀取所有貼文只需要一次 API 呼叫（`GITHUB_TOKEN` 每小時只有 1000 次），檔案在取出後若被改過，sha 對不上就會改走 API，不會讀到舊資料。

## 智慧整理（`src/format/parser.ts`）

純規則式、在瀏覽器執行：

- 先把網址換成等長空白再分析，避免網址中的數字被當成日期。
- 日期：`2026/11/03`、`11月5日`、`10/21`、今天／明天／後天、今晚／明晚、週X／這週X／下週X／下下週X；超過 60 天前的月日視為明年；寫在日期後的星期與實際不符時提醒。
- 時間：`19:00`、`7點半`、`晚上七點`、`下午 1:30～4:30`；沒寫上下午的 1～6 點視為下午；`第一點`、`一點點` 不會被當成時間。
- 每個時間配對最近的日期，再依上下文判斷是「上課／活動」還是「截止」（例如後面接「前繳交」）。補課訊息會優先選「改到」後面的新日期，略過「原本」的舊日期。
- 類型：依關鍵字計分（作業、補課、表單、資源、上課、公告）。
- 內文：已放進欄位的「時間：」「地點：」「連結：」行不重複；項目符號統一成 Discord 清單；句中網址改成文字連結；相對日期改寫成實際日期。

## 測試

`npm test` 執行 80 多個 Vitest 測試：

- `parser.test.ts`：中文日期／時間／類型／地點／連結的各種寫法。
- `crypto.test.ts`：加解密、AAD、金鑰格式、sealed box 與 libsodium 互通。
- `scheduler.test.ts`：以假的 GitHub API 與 Discord 模擬完整流程——到期發送、不重複、等待準時、429、5xx 重試、Webhook 失效、寫入衝突、使用者改期、每週重複、卡住的認領、金鑰錯誤。
- `channels.test.ts`：Webhook 清單匯入、頻道建議、Discord 限制檢查、訊息組裝。
